# Actions

Actions связывают клики по элементам Dashboard и FeatureCard с Python-задачами, фильтрами, ссылками и существующими модалками. Конфигурация задаётся в JSON; визуальный редактор Actions пока отсутствует.

## Определение и вызов

В корне `ConfigContainer`, на странице и в `ConfigModal` поле `actions` содержит переиспользуемые определения с обязательными `id`, `type`, `options`. В поддерживаемом визуальном узле это массив вызовов: ссылка `{ "id": "Calculate" }` или inline-действие `{ "type": "setFilters", "options": { "filters": {} } }`.

`event` необязателен, по умолчанию `click`. Сейчас поддерживается только `click`. При привязке значение вызова перекрывает значение определения. Callback выполняется непосредственно после успешного шага, нового события ему не нужно.

ID ищется от ближайшей модалки к странице и корню своего виджета. Локальное определение заменяет дальнее целиком. Дубли ID внутри одного реестра диагностируются. ID действия независим от ID элемента и slot-id; inline-вызову ID не нужен.

Поле `options` ссылки рекурсивно объединяется с `options` определения: объекты объединяются, массивы заменяются, `null` сохраняется. Если у ссылки есть `callback`, он заменяет базовый; если поля нет — наследует его.

Настройки действия хранятся в `options`. Вложенное поле `options.parameters` у `runTask` и `openModal` содержит аргументы задачи или параметры модалки.

## Четыре действия

| `type` | `options` | Когда запускается callback |
| --- | --- | --- |
| `runTask` | `{ "taskName": "calculate", "fileName": "src/runner.py", "methodName": "calculate", "parameters": { "limit": 100 } }`; `fileName`, `methodName`, `parameters` необязательны; заданные `fileName` и `methodName` — непустые строки | После успешного завершения Python-задачи и чтения её ответа |
| `setFilters` | `{ "filters": { "price": { "value": 100 } } }` | После записи фильтров; загрузки источников ждать не нужно |
| `openUrl` | `{ "url": "https://example.org", "target": "_blank" }` | После передачи адреса браузеру |
| `openModal` | `{ "modalId": "details", "parameters": { "mode": "price" } }` | После открытия/обновления окна, до загрузки его источников |

`runTask.options.taskName` — `name` записи из `currentPage.tasks`, не ID прототипа планировщика. `fileName` и `methodName` в `options` действия — необязательные непустые строки: каждое поле берётся из `options` действия, затем из `ConfigTask`, затем из схемы ресурса. Поэтому файл можно задать один раз в задаче страницы, а метод выбирать кнопкой. Для прямого вызова `runTask(request)` поля запроса имеют тот же приоритет, что и `options` действия.

Поддерживаются Python-ресурсы: при успешном чтении ресурса достаточно `taskResourceSubType: "PythonTask"`, независимо от значения `taskType`; также поддерживаются прежние `taskType: "pythonService"` и `"PythonTask"`. Аргументы объединяются в порядке: дефолты схемы ресурса → сохранённый `userConfiguration` → `ConfigTask.params` → базовые параметры Action → параметры вызова. `taskName`, `fileName` и `methodName` не попадают в Python-аргументы: файл и метод передаются отдельными полями параметров запуска.

Исполнитель читает `GET /scheduler/taskresource/{id}` для получения схемы и `userConfiguration`, даже когда файл и метод заданы явно. Если сервер отвечает **400** с сообщением `Python importMethod is required`, запуск продолжается только при наличии обоих эффективных полей `fileName` и `methodName` из запроса/действия или задачи страницы. В этом случае схема и `userConfiguration` недоступны; используются `ConfigTask.params`, поверх которых накладываются параметры запуска. При отсутствии хотя бы одного поля или при любой другой ошибке чтения ресурса запуск завершается ошибкой.

Одновременно запущенные задачи имеют отдельные результаты, логи и остановку. `TaskContainer.relatedResources` и `responseFilters` используют тот же сервис выполнения.

Общий исполнитель переиспользует подготовку окружения `usePythonSandbox`, запуск прототипа из `useRemoteTask` и опрос `pollSubtaskCompletion`. Для Actions опрос дополнительно ждёт сохранённый `results.response` после статуса Completed и поддерживает отмену ожидания. Обычные вызовы `pollSubtaskCompletion` возвращают конечный статус без ожидания ответа. Сборка уведомлений единая для Actions и TaskContainer; ограничение описания двумя строками сохранено.

`setFilters` заменяет переданные значения фильтров целиком, сохраняя остальные фильтры. Нет toggle, автоматического сброса связанных фильтров или отдельной команды reset. Допустимы существующие формы `SelectedFilters`:

```json
{
  "type": "setFilters",
  "options": {
    "filters": {
      "price": { "value": 120 },
      "categories": { "value": ["A", "B"] },
      "range": { "value": ["low", "high"], "min": 10, "max": 100 },
      "tree": { "value": { "l1": [1], "l2": [42] } },
      "rows": { "value": { "type": "FeatureCollection", "features": [{ "type": "Feature", "id": "1", "geometry": null, "properties": { "price": 120 } }] } }
    }
  }
}
```

`openUrl` выполняет обычный переход, без SPA-маршрутизации. По умолчанию используется `_blank`; поддерживается `_self`. Для цепочки с новой вкладкой окно резервируется во время исходного клика и затем получает URL, в том числе из ответа задачи. Неиспользованное окно закрывается. Если браузер заблокировал окно, пользователь получает уведомление со ссылкой для открытия вручную. Дополнительные вкладки в одной цепочке также могут требовать ручного открытия. Переход `_self` может выгрузить страницу до завершения следующих callback. Разрешены HTTP(S), mailto и tel.

`openModal` открывает только объявленный `modalId`. Внутрь передаются атрибуты записи, данные события, последний ответ задачи, параметры и область действий. Повторное открытие того же ID обновляет одно окно. Источники модалки загружаются в её контексте; поздний ответ для прежней записи не перезаписывает новую. Одноимённый источник страницы сохраняет приоритет над модальным.

Это действие открывает окно без владельца: оно учитывает условную видимость целевой модалки. Окно [[elements#ElementModal|ElementModal]] дополнительно следует видимости вызвавшего элемента и его предков. Подробнее — [[conditional-formatting#Скрытие и состояние|Скрытие и состояние]].

Источники окна хранятся в `ModalDataContext`, отдельно от стора страницы. Ключ запроса свой у каждого источника окна и учитывает резолвленные параметры и условия этого источника, ревизию открытия, параметры слоя и autoSync (слои — `autoSyncLayer` и `autoSyncLayers`, см. [[utils#getDataSourceAutoSyncLayers|getDataSourceAutoSyncLayers]]). Перезапрашивается только источник, чей ключ изменился: смена фильтра не трогает источники окна, которые на него не ссылаются, а пересборка конфига с тем же содержимым запросов не вызывает. `debounce` применяется перед загрузкой; ответ применяется, только пока его запрос остаётся последним для своего источника. После закрытия данные этого host не кэшируются: новое открытие создаёт новую ревизию и запрос. `isModalNotificationAllowed` позволяет хосту применять свою политику уведомлений. Контракт — [[setup#Подключение Actions|Подключение Actions]].

## Данные и подстановки

| Запись | Значение |
| --- | --- |
| `%price` | Актуальный фильтр своего виджета |
| `$dashboard:price` | Фильтр дашборда, в том числе из FeatureCard |
| `{price}` | Атрибут нажатой строки/объекта |
| `#price` | `response.result.features[0].properties.price` последней успешной Python-задачи |
| `$event` / `$event.feature` | Полные данные исходного клика / исходный feature |
| `$params.mode` | Явный параметр открытой модалки |

Формат ответа задачи:

```json
{
  "result": {
    "features": [
      { "properties": { "price": 120, "url": "https://example.org/report/1" } }
    ]
  }
}
```

Подстановки обходят вложенные объекты и массивы параметров. Одиночный токен сохраняет тип (число, boolean, массив, объект); интерполяция в текст даёт строку. URL целиком автоматически не кодируется: сервер должен возвращать готовый URL или корректно кодированные компоненты.

Фильтры читаются перед каждым шагом и условием; callback после `setFilters` уже видит новое значение. Данные клика сохраняются на всю цепочку. `setFilters`, `openModal` и `openUrl` не стирают `#price`; следующий успешный `runTask` заменяет последний ответ. Истории ответов и общего последнего ответа на весь виджет нет.

У графиков `$event` содержит feature, источник, серию, индекс, исходное и отображаемое имя, значение и диапазон. У строк — запись и её стабильный идентификатор. У самостоятельного элемента используются атрибуты его виджета. Те же подстановки доступны в заголовке, содержимом и запросах открытой модалки.

Новые префиксы экранируются обратной косой чертой: JSON `"\\#ff00ff"` означает буквальный цвет. Фрагмент `"/report#section"` сохраняется. В строковых литералах условий токены не раскрываются.

## Callback и условия

Callback может быть одним вызовом либо объектом `условие → вызов` с необязательным `else`. Проверка идёт в порядке записи, запускается только первая истинная ветка. Если совпадений нет, выполняется `else`, а при его отсутствии цепочка завершается успешно. Пустой `{}` не является действием.

Условия — ограниченные JavaScript-выражения, вычисляемые локальным parser/evaluator. В отличие от `query.condition` это не EQL-запрос. Доступны литералы, скобки, `> >= < <= == != === !==`, `&& || !`, арифметика `+ - * / %`, массивы, ограниченный `includes`, чтение свойств/индексов данных и `Date.parse` для ISO-дат. Нет присваиваний, произвольных функций, конструкторов или доступа к браузерному окружению.

```text
#price > %price
["A", "B"].includes({category})
Date.parse(#date) >= Date.parse("2026-01-01")
```

Отсутствующее поле, несовместимые типы, невалидная дата, арифметика или выражение дают `false`. Число `10` не приравнивается к строке `"10"`; явный `null` можно сравнить с `null`. `&&` и `||` вычисляются с short-circuit. Значения подставляются как данные, а не как исполняемый JavaScript.

Подстановки используют общий механизм строк конфигурации; в callback значения читаются из контекста как данные. Условие источника после подстановок отправляется серверу, условие callback вычисляется в браузере. `==` и `!=` работают без преобразования типов, как `===` и `!==`: `10 == "10"` даёт `false`. API парсера и evaluator — [[utils#parseActionCondition / evaluateActionCondition|Утилиты]].

## Полный пример

Перед запуском замените `resourceId` на UUID своего Python-ресурса с аргументами `object_id`, `limit`. Пример содержит реестр, страницу, задачу, фильтр, кнопку и модалку.

```json
{
  "options": {},
  "actions": [
    {
      "id": "CalculatePrice",
      "type": "runTask",
      "options": { "taskName": "calculate_price", "parameters": { "object_id": 1, "limit": "%price" } },
      "callback": {
        "#price > %price": {
          "type": "setFilters",
          "options": { "filters": { "price": { "value": "#price" } } },
          "callback": { "type": "openModal", "options": { "modalId": "price_details", "parameters": { "mode": "calculated" } } }
        },
        "else": { "type": "openUrl", "options": { "url": "#url", "target": "_blank" } }
      }
    }
  ],
  "modals": [
    {
      "id": "price_details",
      "options": { "title": "Цена: #price" },
      "children": [{ "id": "content", "templateName": "ContainersGroup", "options": {}, "children": [{ "id": "priceText", "value": "Результат: #price; режим: $params.mode" }] }]
    }
  ],
  "children": [
    {
      "id": "pages",
      "templateName": "Pages",
      "options": {},
      "children": [
        {
          "id": "page1",
          "templateName": "ContainersGroup",
          "options": { "title": "Actions" },
          "tasks": [{ "name": "calculate_price", "resourceId": "00000000-0000-0000-0000-000000000001", "subType": "PythonTask", "params": {} }],
          "filters": [{ "id": "price", "name": "price", "valueType": "single", "defaultValue": 100 }],
          "children": [{ "id": "calculate", "type": "button", "value": "Рассчитать", "actions": [{ "id": "CalculatePrice" }] }]
        }
      ]
    }
  ]
}
```

## Одна задача, разные методы

Фрагмент страницы ниже использует один ресурс со скриптом `src/runner.py`. Замените `resourceId` на ID своего Python-ресурса; фильтр `project` должен быть объявлен в виджете. Кнопки наследуют файл задачи и передают разные методы. После успешного ответа с `status: "ok"` callback открывает `#url`.

```json
{
  "tasks": [
    { "name": "runner", "resourceId": "00000000-0000-0000-0000-000000000001", "fileName": "src/runner.py" }
  ],
  "children": [
    {
      "id": "btn_deploy_map",
      "type": "button",
      "value": "Создать карту проекта",
      "actions": [{
        "type": "runTask",
        "options": { "taskName": "runner", "methodName": "deploy_map", "parameters": { "project_id": "%project" } },
        "callback": {
          "#status === 'ok'": { "type": "openUrl", "options": { "url": "#url", "target": "_self" } }
        }
      }]
    },
    {
      "id": "btn_build_report",
      "type": "button",
      "value": "Собрать отчет",
      "actions": [{
        "type": "runTask",
        "options": { "taskName": "runner", "methodName": "build_report", "parameters": { "project_id": "%project" } },
        "callback": {
          "#status === 'ok'": { "type": "openUrl", "options": { "url": "#url" } }
        }
      }]
    }
  ]
}
```

## Поверхности клика и совместимость

| Узел | Событие |
| --- | --- |
| ChartContainer | Существующие сегменты pie/bar/stack и соответствующие записи легенды |
| DataSourceContainer, DataSourceProgressContainer | Конкретная запись `innerTemplate` |
| StructuredDataContainer | Вся строка таблицы; при `options.editMode` Actions отключены |
| ProgressContainer, RoundedBackgroundContainer | Контейнер |
| ElementIcon, ElementSvg, ElementImage, ElementLink, ElementButton | Сам элемент |

У графика применяется `chart.actions ?? ChartContainer.actions`: локальный массив элемента заменяет привязку контейнера, пустой массив отключает наследование. Легенда исполняет действия связанного графика. Действия строк таблицы задаются `StructuredDataContainer`, а `ElementTable` только передаёт событие строки. Произвольное поле `actions` у остальных шаблонов не добавляет обработчик клика.

Настроенные click Actions перекрывают стандартную фильтрацию/переход. Без Actions прежнее поведение сохраняется. Ближайший вложенный обработчик имеет приоритет: иконка не запускает Action родительской плитки. Action-only кнопка видна без старого URL. Линейным графикам новые клики не добавляются; синтетическое «Другое» не запускает Actions. Обычная запись с таким названием остаётся кликабельной.

Массив действий выполняется последовательно: каждый вызов ждёт всей callback-цепочки предыдущего. Цикл `A → B → A` разрешён; исполнитель периодически возвращает управление браузеру, доступна остановка цепочки.

Повторный клик отменяет прежнюю цепочку только того же элемента/строки и запускает новую. Разные строки независимы даже с одинаковым `action.id`. Клик сегмента и соответствующей записи легенды считается одним источником. Refetch строки сам по себе цепочку не отменяет.

При смене страницы, проекта, объекта или закрытии карточки callback прекращаются; серверная задача продолжает наблюдаться общим сервисом. Остановка пользователем и повторный клик запрашивают остановку серверной задачи. Ошибки показываются общим уведомлением; после ошибки последующих действий нет. Только успешное завершение запускает callback.

## Подключение и проверка

Штатные `GlobalProvider`, `DashboardProvider`, `FeatureCardProvider` подключают task-runtime, Actions и модалки. Хост передаёт `getActionFilters` (синхронный getter), `actionContextKey` (проект/страница/объект), `actionsActive` (открыт ли виджет). Смена ключа/активности прекращает текущие продолжения и закрывает окна; синхронный getter позволяет следующему шагу прочитать результат `setFilters` до перерисовки React. Подробнее — [[setup#Подключение Actions|Подключение Actions]].

Конфиги проверяются [[utils#validateDashboardActions|validateDashboardActions]]: возвращается `ActionValidationIssue[]` с `path`, `code`, `message`, `ownerId?`, `severity`. У `runTask.options` поля `fileName` и `methodName` проверяются как необязательные непустые строки; значения только из пробелов не допускаются. Эта проверка относится к `options` действия, а не к полям `ConfigTask`. Клиентский `validateDashboardConfig` включает эти проверки и отображает их с кодом `invalid-action`; реестры обходятся отдельно от визуальных узлов. Совпадение ID действия и визуального узла допустимо, дубли определений внутри одного реестра — ошибка. Публичные контракты — [[types#Типы Actions|Типы Actions]].

Storybook: раздел **Actions / Runtime**. Примеры используют настоящий исполнитель с моками API задач. Ручная приёмка: успешная цепочка и ветка else; ошибка задачи; остановка и повторный клик; две независимые строки; смена страницы; открытие одной модалки для разных записей; URL из ответа; одинаковые клики графика/легенды; таблица в обоих режимах; те же сценарии в FeatureCard.
