# Условное форматирование

`conditions` меняет внешний вид узла Dashboard или FeatureCard по состоянию фильтров, атрибутов и источников данных. Поле доступно у корня, страниц, контейнеров, элементов, слотов, шапок и модальных окон. Правила задаются в JSON; отдельного визуального редактора условий нет.

## Формат и порядок

```json
{
  "id": "sales",
  "templateName": "ContainersGroup",
  "options": { "innerPadding": false },
  "style": { "borderRadius": 8 },
  "conditions": {
    "%amount >= 100": {
      "options": { "innerPadding": false },
      "style": { "outline": "2px solid #df9d28" }
    },
    "%amount > 0": {
      "options": { "innerPadding": true },
      "style": { "outline": "2px solid #298ac4" }
    },
    "else": { "visibility": false }
  },
  "children": [
    { "id": "alias", "type": "text", "value": "Продажи" },
    { "id": "value", "type": "text", "value": "%amount" }
  ]
}
```

Ключи объекта — выражения, значения — переопределения. Выражения проверяются в порядке записи. Применяется только первая истинная ветка: при `amount = 120` побеждает золотая обводка без внутреннего отступа, хотя второе выражение тоже истинно. `else` — резервный ключ; положение в объекте не меняет его смысл. Он применяется, если ни одно выражение не подошло. Без подходящей ветки и без `else` сохраняется базовое оформление.

Переопределение поддерживает только три поля:

| Поле | Поведение |
|---|---|
| `options` | Рекурсивно объединяется с базовыми опциями; на типизированном компоненте принимает его собственные опции |
| `style` | Рекурсивно объединяется с базовым React `CSSProperties`; свойства пишутся в camelCase |
| `visibility` | `false` скрывает узел вместе с его занимаемым местом; `true` разрешает показ |

Объекты объединяются на каждом уровне, массивы заменяются целиком, `null` сохраняется как явное значение. Незаданные поля остаются базовыми. Например, `options: { "axis": { "title": null } }` обнуляет только заголовок оси, сохраняя её остальные настройки. Обнулённая настройка дальше обрабатывается обычным компонентом; это не удаление свойства из JSON.

Остальные поля узла — `id`, `type`, `templateName`, `children`, `value`, `defaultValue`, `actions`, источники данных — через условный override менять нельзя. При изменении фильтра оформление каждый раз рассчитывается заново от исходного конфига; ветки не накапливаются.

## Выражения и источники

Используется тот же ограниченный parser/evaluator, что в [[actions|Actions]]. Он поддерживает скобки, `!`, числовые `+`/`-`, арифметику, сравнения, `&&`/`||`, чтение свойств и индексов, массивы, `.includes(...)` и `Date.parse(...)`. Произвольный JavaScript не выполняется. `==` и `!=` сравнивают без преобразования типов, как `===` и `!==`.

| Подстановка | Источник |
|---|---|
| `%filter`, `%range.min`, `%range.max` | Фильтры текущего виджета |
| `$dashboard:filter`, `$dashboard:filter.prop` | Фильтры ближайшего Dashboard |
| `$dashboard:source-name:field` | Поле первой строки источника Dashboard; имя источника может содержать точки и дефисы |
| `$card:layer.name:field` | Атрибут выбранного объекта карточки указанного слоя |
| `{attribute}` | Атрибут текущего объекта |
| `%geometry`, `%extent`, `%zoom`, `%project.name`, `%project.alias` | Системные значения из GlobalContext |

Примеры: `%count % 5 === 2`, `[1, 2].includes(%district)`, `$dashboard:sales:total > 100`, `Date.parse({date}) >= Date.parse('2026-01-01')`.

Action-подстановки `#result`, `$event` и `$params` запрещены. Проверяется весь AST, включая ветки, которые вычисление могло бы пропустить: `true || $event.value` невалидно. Символы внутри строкового литерала остаются обычным текстом: `'#result' === '#result'` допустимо.

Ошибка разбора или неизвестное значение делают вычисляемую ветку ложной; рендер не падает. Правила чтения пустых/null-значений и короткого вычисления `&&`/`||` совпадают с Actions и общей системой [[concepts|подстановок]]. Условие источника `dataSources[].condition` сохраняет свой прежний серверный смысл и не относится к `conditions` визуального узла.

## Значения override — буквальные

В `options` и `style` выбранной ветки строки не получают подстановку. Например, `"options": { "title": "%filter" }` задаёт именно текст `%filter`. Базовые `value`, `defaultValue` и строковые опции продолжают обычную подстановку. Проверяется только выражение в ключе `conditions`; содержимое override — статический payload.

Для этого отрендеренный узел несёт служебный Symbol со списком переопределённых ключей опций. Обычное копирование через spread сохраняет отметку; сериализация JSON её не записывает. В конфигурацию нужно сохранять исходный authoring-узел, а не временный результат оформления.

## Загрузка и область вычисления

Пока `isDataLoading` текущего виджета истинно, применяется базовый конфиг: условия и `else` не вычисляются. Флаг покрывает первоначальную загрузку и выполняющиеся запросы, включая автообновление источников. В страничном загрузчике Dashboard из client-new ожидание таймера debounce не отслеживается как запрос: отслеживание начинается при фактическом запуске загрузчика. В модальном окне локальный флаг учитывает ожидание debounce его источников, выполняющиеся запросы и загрузку виджета. Обычные `loading`/`isLoading` продолжают управлять спиннерами; этот дополнительный флаг нужен для согласованного оформления.

После завершения текущей загрузки правила пересчитываются по актуальному снимку `ConfigStringSources`. Этот снимок собирает `useConfigStringSources`; интеграцию выполняет `useConditionalConfig(type, node)`.

У `DataSource` и `DataSourceProgress` правила хоста и его потомков разрешаются один раз перед размножением шаблона по записям. Отрендеренные узлы уже не содержат `conditions`, поэтому условия не запускаются повторно для каждой строки. `{attribute}` в таком правиле относится к объекту текущего виджета; строковые значения самих элементов могут по-прежнему использовать атрибуты записи обычным механизмом рендера.

`containerId` — указатель на существующий узел. Условные правила задавайте на целевом контейнере. Конфиг поиска целей тоже разрешается на границе рендера по источникам хоста до обработки записей; атрибуты конкретной строки используются только для обычной подстановки её значений. Поэтому цель ссылки за пределами DataSource-поддерева получает одинаковое условное оформление во всех строках.

Обход затрагивает только `children`, `header` и `modals`. Поля данных, описания источников, Actions и сами значения override не рассматриваются как вложенные визуальные узлы. Исходный конфиг не меняется; ветви без условий сохраняют исходные ссылки.

## Скрытие и состояние

`visibility` по умолчанию разрешает показ. `false` скрывает узел вместе с его местом в раскладке. Стили применяются к существующим корням элементов и владельцам слотов; дополнительные DOM-обёртки для условного форматирования не создаются. Текст без собственного элемента и скрытые фильтры исключаются из вывода. Сохранение локального состояния при скрытии не гарантируется. У текста в горизонтальном ряду нет отдельного CSS-корня; для стиля используется существующий владелец слота, если он предусмотрен шаблоном.

Стиль фильтра передаётся через существующий API его компонента. У числового диапазона он применяется к слайдеру, а не ко всей группе с подписью и полями. Компонент диапазона дат не принимает стиль корня; для его настройки доступны штатные `options`. `visibility` работает для обоих фильтров.

Открытое модальное окно с владельцем (например, окно от `ElementModal`) следует текущей видимости вызвавшего его элемента и всех предков. Видимость передаётся в существующий `isOpen` компонента `Dialog`; отдельной portal-обёртки для скрытия нет. Собственная `visibility` целевой модалки также учитывается. Сохранение локального состояния содержимого при скрытии не гарантируется.

`ownerKey` связывает запись открытия с владельцем, `ownerVisible` хранит его текущую видимость. Скрытие владельца сохраняет запись, снимок контекста и ревизию; события закрытия не возникает. Это не гарантирует сохранение локального состояния содержимого `Dialog`.

Окно, открытое Actions или программно без владельца, зависит от условной видимости самой целевой модалки. Оно не наследует отдельно отслеживаемую видимость инициатора.

Шапки применяют стиль/видимость к корневой обёртке. Стиль скалярного содержимого авторского слота применяется к его существующему владельцу, а стиль React-элемента — к собственному корню элемента; видимость слота управляет его владельцем в обоих случаях. `FeatureCardDefaultHeader` теперь принимает `title` и `description`: без слота сохраняется штатный текст, при `noFeature` — «Объектов не найдено» / «Все слои». Авторский скрытый или пустой слот не включает fallback. Нажатие на видимый заголовок выбранного объекта по-прежнему приближает карту; семантика Background/Slideshow сохраняется. Подробности — [[headers#FeatureCardDefaultHeader|Шапки]].

Пример в Storybook: `Conditional Formatting / First matching rule`. Кнопки устанавливают `score` в 0, 5 или 12; первые две ветки меняют внутренний отступ и обводку `ContainersGroup`, условия текстового элемента — его цвет; `else` скрывает блок. Можно раскрыть Markdown, скрыть блок и вернуть его, проверив сохранение локального состояния.

## Типы и чистые функции

Из `@evergis/react` экспортируются:

| API | Назначение |
|---|---|
| `ConfigConditions<Options>` | Объект выражений с override заданного типа опций |
| `ConfigConditionalOverride<Options>` | Только `options`, `style`, `visibility` |
| `ConfigConditionalPartial<Value>` | Рекурсивные частичные поля и явный null; массив заменяется целиком |
| `ConfigConditionalFormatting<Options>` | Общие `conditions?` и `visibility?` визуального узла |
| `resolveConditionalFormatting(node, sources, isReady = true)` | Возвращает дерево для рендера, сохраняя исходный authoring-конфиг |
| `isConditionallyVisible(node?)` | По умолчанию true; false только при `visibility === false` |
| `getConditionalVisibilityStyle(node?)` | `{ display: "none" }` для скрытого узла, иначе undefined |
| `validateDashboardConditionalFormatting(config)` | Общая проверка выражений и допустимого payload без React-рендера |

`ConfigContainer`, `ConfigContainerChild`, `ConfigContainerHeader`, `ConfigModal` поддерживают правила. Per-component типы и [[types#Дискриминированный union `DashboardChild`|DashboardChild]] проверяют override по конкретному набору опций компонента.

## Проверка конфигурации

В client-new `validateDashboardConfig` включает общий валидатор и возвращает ошибки с кодом `invalid-conditional-formatting`, точным `path`, `parentId` владельца и `severity`. Он проверяет root/header/children/modals; ловит неверный формат `conditions`, синтаксис выражений, action-only токены, посторонние ключи override и неверные типы `options`/`style`/`visibility`. Строки внутри допустимого статического payload не проверяются как выражения.

Для серверного инструмента или отдельного теста используется чистая точка входа без UI:

```ts
import { validateDashboardConditionalFormatting } from "@evergis/react/dist/dashboardConditionalFormatting";

const issues = validateDashboardConditionalFormatting(config);
// { path, ownerId?, message, severity }[]
```

Клиентская dev-проверка выводит диагностику, сохраняя прежнее поведение рендера. Основной порядок проверки описан в [[setup#Проверка конфигурации в client-new|Подключении]].
